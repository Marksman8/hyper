# AURA v0.1 — Architecture

Status: **active** · Target: first working local assistant · Date: 2026-09-05

---

## 1. What v0.1 is

A **local-first conversational runtime with a replaceable brain**.

v0.1 deliberately contains no vision, no voice, no computer control, no learning,
no evolution. It exists to prove one thing:

> AURA can hold a persistent, memory-backed conversation using an open-weight
> model running on this machine, with no dependency on any hosted API — and the
> model underneath can be swapped without touching AURA's code.

Everything later in the roadmap plugs into the seams established here.

## 2. Process topology

AURA is **two processes**, not one.

```
  +----------------------------------------------------------+
  | Client  (v0.1: CLI · v0.1.1: tray overlay · later: IDE)   |
  +-----------------------+----------------------------------+
                          |  HTTP + SSE, bearer token, loopback only
                          v
  +----------------------------------------------------------+
  | AURA CORE          python -m aura serve      :8760        |
  |                                                           |
  |   api/         FastAPI surface, auth, SSE streaming       |
  |   core/        Orchestrator · event bus · turn state      |
  |   memory/      SQLite: sessions, turns, facts             |
  |   security/    Permission levels · audit log · secrets    |
  |   models/      LLMProvider interface + registry           |
  |   runtime/     Model-server supervisor · resource watch   |
  +-----------------------+----------------------------------+
                          |  OpenAI-compatible HTTP  <-- the replaceability seam
                          v
  +----------------------------------------------------------+
  | MODEL SERVER       llama-server               :8081       |
  |   GGUF Q4_K_M on RTX 5060 (8 GB) · CUDA 12.8 (sm_120)     |
  +----------------------------------------------------------+
```

**Why two processes and not one.**

1. *Lifecycle independence.* Restarting AURA core after a code edit takes
   ~400 ms. Reloading a 5 GB model takes ~20 s. During development you will
   restart core hundreds of times a day. Coupling them is the single most
   expensive design mistake available here.
2. *Crash isolation.* A CUDA OOM or a llama.cpp segfault kills the model server;
   AURA core survives, reports `model: unavailable`, and can restart it.
3. *It IS the replaceability seam (spec §32).* The boundary is a wire protocol,
   not a Python import. llama.cpp, Ollama, LM Studio, vLLM-in-WSL, a second
   machine on the LAN, or a future fine-tuned AURA model all satisfy it.
4. *Memory accounting.* With 15.7 GB system RAM, being able to kill the model
   process and keep the assistant's state alive matters.

The cost is one HTTP hop (~0.3 ms on loopback, invisible next to token latency)
and a supervisor to manage. Worth it.

## 3. The replaceability seam

Spec §32 is the load-bearing rule. It is enforced at **two** levels:

```
        aura.core.orchestrator
                 |  depends only on
                 v
        aura.models.base.LLMProvider          <-- level 1: Python ABC
                 |
    +------------+-------------+------------------+
    v            v             v                  v
 OpenAICompat  Echo        (future)            (future)
 Provider      Provider    Transformers        AURA-tuned
    |          in-process   in-process         endpoint
    |          test double
    v
 OpenAI-compatible HTTP                        <-- level 2: wire protocol
    |
    +-- llama.cpp llama-server   (v0.1 default)
    +-- Ollama
    +-- LM Studio
    +-- vLLM (WSL2 / remote host)
```

**Enforced invariant:** no module outside `aura/models/providers/` may import an
inference library or reference a model filename. A test asserts this.

## 4. Component contracts

| Component | Owns | Must not |
|---|---|---|
| `api/` | HTTP surface, auth, SSE framing | contain reasoning logic |
| `core/orchestrator` | turn lifecycle, prompt assembly, memory read/write | know which model or provider is in use |
| `memory/` | durable state, retrieval | make policy decisions about what is worth remembering |
| `security/` | permission levels, audit trail, token | be bypassable by any other component |
| `models/` | provider abstraction, model config | know about sessions, users, or tools |
| `runtime/` | subprocess supervision, resource sampling | be required for core to boot |

The orchestrator is the only component that knows the *shape of a turn*. This is
where the agent loop (Phase 4) grows; in v0.1 the loop has exactly one step.

## 5. Data model (v0.1)

SQLite via the stdlib `sqlite3`, WAL mode. No ORM, no vector DB yet — spec §14
says choose the simplest architecture that satisfies the requirement, and v0.1's
requirement is "conversations survive a restart".

```
sessions(id, title, created_at, updated_at, metadata_json)
turns(id, session_id, role, content, created_at,
      model, provider, prompt_tokens, completion_tokens,
      latency_ms, finish_reason, error, metadata_json)
facts(id, scope, key, value, confidence, evidence_count,
      source, permanence, created_at, last_confirmed_at)
audit(id, ts, actor, action, permission_level, decision,
      target, detail_json)
```

`facts` is deliberately present in v0.1 even though nothing writes to it
automatically. It carries the `confidence` / `evidence_count` / `permanence`
columns from spec §15 and §16 so Phase 6 is a *feature* addition, not a
migration. `permanence` is one of `session`, `temporary`, `long_term`,
`permanent` — the §16 distinction, encoded in the schema from day one because
retrofitting it later means re-labelling every stored fact by hand.

Vector search (`sqlite-vec` extension, in-process, ~1 MB) arrives in Phase 6
when there is enough stored text for retrieval to beat a `LIKE` query. Adding
Chroma or Qdrant now would mean a second server process for a table with 40 rows.

## 6. Security foundation (spec §23, established now)

Present in v0.1 even though nothing dangerous exists yet, because retrofitting a
permission system around code that assumed it was absent never works.

- **Bind loopback only.** `127.0.0.1`, never `0.0.0.0`.
- **Bearer token on every route** except `/healthz`. Auto-generated into
  `var/secrets/api_token` on first run.
- **Permission levels 0-4** defined as an enum now (spec §8). Every future tool
  declares one. All v0.1 operations are LEVEL 0/1.
- **Append-only audit log.** Every request and every model call gets a row.
  This is the substrate for §25 ("why did AURA do this?").
- **No secret ever reaches the model.** Config redacts on serialization.
- **Emergency stop** (§13) as a first-class concept: one flag that halts all
  outbound model calls and, later, all tool execution.

## 7. Hardware budget

Measured on this machine: RTX 5060 Laptop 8151 MiB VRAM, 15.7 GB RAM,
i7-13700HX (16C/24T), Windows 11.

| Consumer | VRAM | RAM |
|---|---|---|
| Qwen3-4B-Instruct Q4_K_M, 8k ctx | ~3.1 GB | ~0.3 GB |
| KV cache @ 8k (q8_0) | ~0.4 GB | — |
| AURA core (Python, no torch) | 0 | ~0.12 GB |
| CLI client | 0 | ~0.04 GB |
| **v0.1 total** | **~3.5 GB** | **~0.5 GB** |
| Headroom for Phases 2 and 5 | ~4.6 GB | — |

**The binding constraint is 15.7 GB system RAM, not 8 GB VRAM.** Chrome plus
VS Code plus Windows routinely occupy 12-13 GB; free RAM measured at 2.3 GB
during this session. Consequences, adopted as standing rules:

- **Exactly one always-resident LLM**, and it is small (4B at Q4 or less).
- Every other model (STT, TTS, VLM, embeddings) is **load-on-demand with idle
  eviction**. `runtime/` owns this policy from v0.1 forward.
- An 8B model is a *foreground* mode you switch into, not the default.
- Phase 5 multi-monitor vision will be sampling-based and heavily gated. The
  §11 "continuously understand three monitors" design does not fit this box as
  literally written; it becomes event-triggered snapshots with change detection.

## 8. Model choice for v0.1

Default: **Qwen3-4B-Instruct-2507, Q4_K_M GGUF**.

Rationale: strong tool-calling and structured-output behaviour, which is exactly
what Phases 3-4 need; fits with room to spare; ~40-60 tok/s expected on this GPU.
Alternatives kept one config line away in `config/models.yaml`: Qwen3-8B Q4_K_M
(fits at ~5.0 GB, slower, better reasoning), Llama-3.1-8B-Instruct,
Mistral-7B-Instruct.

The choice is a config value. If it ever becomes a code value, the architecture
has failed.

## 9. Explicitly out of scope for v0.1

Vision · voice · tools · computer control · agent loop · learning · genetic
algorithms · fine-tuning · multi-agent · vector search · desktop overlay
(v0.1.1). Each has a reserved seam and nothing more.

## 10. Deferred decisions

| Decision | Deferred to | Why |
|---|---|---|
| Desktop UI toolkit (PySide6 vs Tauri) | v0.1.1 | Needs a working core to build against; RAM cost measured, not guessed. |
| Vector store | Phase 6 | Needs data volume to justify a second dependency. |
| Agent state machine shape | Phase 4 | Needs real tools to constrain the design. |
| GA vs hill-climbing | Phase 9 | Needs the Phase 8 benchmark harness to produce a fitness signal first. |
